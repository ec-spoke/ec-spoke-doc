    ログ基盤設計

    目的と前提

    • Laravel 12 / Monolog ベースでログ管理を行うにあたり、ECCUBE で得た知見を踏まえて運用しやすい設計指針をまとめる。
    • 商品管理・会員管理・決済連携など複数ドメインで共通利用できるチャネルとレベル戦略を整備し、障害解析と日常運用の両立を図る。
    • 既存ドキュメント「ログ基盤・設定アクセス・多言語対応 方針」は横断観点の備忘録として維持し、本書でログ領域を詳細化する。

    ログチャネル戦略

    • 標準チャネル (site)
    • 全体的なアプリ操作・業務処理の結果を記録する。
    • INFO レベルまで有効化し、ユーザー操作やジョブ実行のトレースを確保。

    • コンテキストに request_id、user_id、feature などを付与して検索性を高める。

    • フロントエンド (frontend)

    • 明示的にチャネル指定した場合のみ出力。（EC-Spoke側では通常使わない）

    • 管理画面 (admin)

    • 明示的にチャネル指定した場合のみ出力。（EC-Spoke側では通常使わない）

    • 決済 (payment)（将来予定）

    • 決済ゲートウェイのリクエスト／レスポンス概要を記録するタイミングや粒度は今後定義する。

    • 秘匿情報はマスクする方針のみ先に決めておく。

    • 監査／セキュリティ (audit)（将来予定）

    • パスワード変更、ロール付与、API キー発行など重要操作のログ設計は今後検討する。
    • 変更前後の値差分や操作者、実行元 IP などを記録する方針を検討課題として残す。

    チャネル別設定方針

    チャネル driver 保存先 既定フォーマット レベル ローテーション 用途・備考
    site daily storage/logs/site.log 規定値 line 規定値 info 30 日 アプリ共通の操作ログ（サーバーログ）。ExLog::info() など明示チャネル無しの呼び出しはすべて site チャネルに出力される。
    frontend daily storage/logs/frontend.log 規定値 line 規定値 info 30 日 ECフロント向け。ExLog::channel('frontend')->info(...)のように明示的にチャネルを指定した場合のみ使用される。
    admin daily storage/logs/admin.log 規定値 line 規定値 info 30 日 管理画面向け。ExLog::channel('admin')->info(...)のように明示的にチャネルを指定した場合のみ使用される。
    payment 未定 未定 未定 未定 未定 決済連携ログの取得タイミング・フォーマットは後日策定。秘匿情報マスクのみ確定。
    audit 未定 未定 未定 未定 未定 監査ログの設計は後日検討。重要操作を対象とする方針のみ決定。

    環境変数（ログ関連）

    本設計では、フォーマットとレベルは単一キーで全チャネル共通に制御する。

    採用キー（全チャネル共通）:

    ログレベル

    • EX_LOG_LEVEL（例: info, debug）
    • 環境変数を設定しない場合、APP_ENVに基づいて自動的にデフォルト値が設定されます
    • prod, stage, develop: デフォルト info
    • testing: デフォルト debug（PHPUnitテスト環境用）
    • 環境変数を設定することで、デフォルト値を上書き可能です

    フォーマット（json or line）

    • EX_LOG_FORMAT（例: line）

    ペイロード制限

    リクエストのペイロード（request()->all()）や大きなコンテキスト配列をログに記録する際、サイズが無制限に膨らむとストレージや検索パフォーマンスに悪影響を及ぼす。以下の環境変数で制限を設定し、適切なサイズに抑える。

    • EX_LOG_PAYLOAD_MAX_STRING_LENGTH=1000
    • 個別の値の文字列長の上限（文字数）
    • 例: 長い説明文やJSONテキストが1000文字を超える場合、末尾が省略される

    • デフォルト: 1000文字

    • EX_LOG_PAYLOAD_MAX_ARRAY_DEPTH=20

    • 配列のネスト階層の深さ制限
    • 例: 20階層を超えてネストされた配列は、それ以降の階層が省略される

    • デフォルト: 20階層

    • EX_LOG_PAYLOAD_MAX_ARRAY_SIZE=100

    • 配列の要素数の上限
    • 例: 100要素を超える配列は、主要要素のみ記録される

    • デフォルト: 100要素

    • EX_LOG_PAYLOAD_MAX_TOTAL_SIZE=10240

    • コンテキスト全体のサイズ上限（バイト）
    • 例: コンテキスト配列全体が10KBを超える場合、主要キーのみ記録される
    • デフォルト: 10240バイト（10KB）

    これらの制限はExLog::log()内で実装され、すべてのログ出力に共通して適用される。制限を超えた場合、自動的に省略・切り詰め処理が行われ、ログ出力が継続される。

    ログレベルと環境別ポリシー

    環境 デフォルトレベル 理由
    prod info ワーニング以上のみだと復旧時に操作履歴が追えないため、最低限の業務トレースを保持。通知閾値は warning 以上に設定しノイズを抑制。
    stage info 本番環境と同等のログレベルで運用。必要に応じて環境変数 EX_LOG_LEVEL=debug で一時的に詳細ログを有効化可能。
    develop info 開発環境でも本番に近いログレベルで運用。必要に応じて環境変数 EX_LOG_LEVEL=debug で詳細ログを有効化可能。
    testing debug PHPUnitテスト環境用。テスト実行時の詳細な挙動を把握するため。

    環境変数の自動設定

    • APP_ENVに基づいて、config/ecspoke.phpで自動的にデフォルトログレベルが設定されます
    • 環境変数 EX_LOG_LEVEL を設定することで、デフォルト値を上書き可能です

    • 環境変数を設定しない場合、APP_ENVに応じたデフォルト値が自動的に適用されます

    • レベル選定ガイド

    • info: 正常系の業務イベント（在庫引当成功、決済リクエスト送信など）。
    • notice: 予兆レベル（リトライ成功、フォールバック利用など）。
    • warning: 想定外の入力や回復したエラー（API リトライ失敗→フォールバック成功）。
    • error: 処理失敗・要対応事象。
    • critical: 直ちに対応が必要な障害（決済不可、データ損失懸念）。
    • alert: 緊急対応が必要な重大な障害（セキュリティ侵害、重要なサービス停止など）。
    • emergency: システム全体が使用不可となる重大な障害（全サービス停止、データベース完全停止など）。

    ログ出力ラッパー（クラス名：ExLog）

    • 目的
    • ログメッセージの命名規則、チャネル選択、外部通知の有無を統一し、開発者が Log ファサードを直接呼び出さなくても済むようにする。

    • 共通のフォーマット／プロセッサはチャネル設定で付与しつつ、アプリ固有ルール（メッセージ形式やチャネル判定など）をラッパーで担保する。

    • 役割

    • ExLog::info('order.created', [...]) のように、英語ドット区切りのメッセージを必須とする。
    • 共通メソッドは debug / info / notice / warning / error / critical / alert / emergency を提供し、PSR-3 のレベルをすべてカバーする。
    • チャネル選択は、ExLog::info()など明示的にチャネルを指定しない場合、すべて site チャネルに出力される。
    • 明示的にチャネルを指定する場合は ExLog::channel('frontend')->info(...) や ExLog::channel('admin')->info(...)、ExLog::channel('payment')->info(...) のようにメソッドチェーンで指定する。この場合、指定されたチャネルのみに出力される。

    • 特定イベントを外部通知（Slack 等）へ送る場合も ExLog の内部にルールを集約し、呼び出し側が意識せず利用できるようにする（将来予定）。

    • 実装構造

    • app/Logging/ExLog.php: メインのログ出力ラッパークラス。静的メソッドとチャネル指定のエントリーポイントを提供。
    • app/Logging/ChannelLogger.php: 明示チャネル指定用の軽量ロガー。ExLog::channel('frontend')->info(...) のようなチェーンを安全に解決する独立クラス。

    • 最終的に Laravel の Log ファサードへ委譲し、設定されたプロセッサとフォーマッタが適用される。

    • メソッドシグネチャ

    • すべてのログレベルメソッドは以下の統一されたシグネチャを持つ： 
      ExLog::debug(string $message, array $context = [], ?array $mask = null, ?array $callerOverride = null): void
ExLog::info(string $message, array $context = [], ?array $mask = null, ?array $callerOverride = null): void
ExLog::notice(string $message, array $context = [], ?array $mask = null, ?array $callerOverride = null): void
ExLog::warning(string $message, array $context = [], ?array $mask = null, ?array $callerOverride = null): void
ExLog::error(string $message, array $context = [], ?array $mask = null, ?array $callerOverride = null): void
ExLog::critical(string $message, array $context = [], ?array $mask = null, ?array $callerOverride = null): void
ExLog::alert(string $message, array $context = [], ?array $mask = null, ?array $callerOverride = null): void
ExLog::emergency(string $message, array $context = [], ?array $mask = null, ?array $callerOverride = null): void

    • 引数説明:

      • $message: ログメッセージ（英語ドット区切り形式を推奨、例: 'order.created'）
      • $context: 追加情報の配列（例: ['order_id' => 123]）
      • $mask: マスク対象のキーを指定する配列（例: ['email', 'phone']）。指定されたキーの値がマスク処理される。
      • $callerOverride: 呼び出し元情報を明示的に上書きする配列（通常は自動検出されるため不要）。形式: ['class' => '', 'function' => '', 'file' => '', 'line' => 0]

    • フォーマット切り替え

    • config/logging.php のチャネル設定に format（line or json）を設け、共通 tap クラス（App\Logging\ApplyFormatter）で LineFormatter／JsonFormatter を出し分ける。
    • .env の EX_LOG_FORMAT を切り替えることで、ラインログ ⇔ JSON ログを環境ごとに簡単に変更できる。

    • 実装方法:

      • ApplyFormatter クラスは Illuminate\Log\LogManager の tap メソッドで呼び出される
      • ApplyFormatter クラス内で $channel->getConfig('format') または env('EX_LOG_FORMAT', 'line') を取得し、line の場合は LineFormatter、json の場合は JsonFormatter を適用する
      • 実装場所: app/Logging/ApplyFormatter.php

    • 使用例

    • 基本メソッド（チャネル自動判定、site チャネルに出力）： 
      ExLog::info('order.created', ['order_id' => 123]);
    • メソッドチェーンでチャネル明示指定： 
      ExLog::channel('payment')->info('payment.processed', ['order_id' => 123]);

    • マスク処理を指定： 

      ExLog::info('user.registered', ['email' => $user->email, 'phone' => $user->phone], ['email', 'phone']);

    • マスク処理

    • ExLogクラス内で明示的マスク処理を実装する。これにより、ExLog経由のログ出力には指定されたキーに対してマスク処理が適用される。
    • 明示的マスク（第3引数 $mask で指定）:
      • ExLog::info() などのメソッドの第3引数でマスク対象のキーを配列で指定
      • 例: ExLog::info('order.created', ['email' => $email, 'phone' => $phone], ['email', 'phone'])
      • ExLogクラス内で第3引数のマスク配列を処理し、指定されたキーをマスクしてからLaravelのLogファサードに渡す
      • 実装場所: app/Logging/ExLog.php の applyMasking() メソッド
    • マスクパターン:
      • email: メールアドレス形式のマスク（例: t***@example.com）。キー名が email の場合に自動適用。
      • phone: 電話番号形式のマスク（例: 090-****-1234）。キー名が phone, phone_number, tel の場合に自動適用。
      • partial: 部分表示マスク（例: ab****cd）。先頭2文字と末尾2文字を表示し、中間を * でマスク。デフォルトパターン。
    • 例外の扱い:
      • context 配列の exception キーに \Throwable または \Exception オブジェクトが含まれる場合、マスク処理の対象外となる（Monologが自動的に処理）。
    • 再帰的マスク:
      • context 配列内のネストされた配列に対しても再帰的にマスク処理が適用される。

    • オブジェクトログは toLogContext() 実装（DTO）を用意し、JSON 化時のフィールド統一を図る。

    • 呼び出し元検出

    • ExLogクラスは3つの呼び出し元検出メソッドを提供：
      • findCallerFrame(): 通常のログ出力時に呼び出し元を自動検出（ExLog::info() などの呼び出し箇所を特定）
      • findCallerFromStack(): トランザクションリスナーなどのイベントリスナーから呼び出される場合に使用（DB::commit() や DB::rollBack() を呼び出した行を取得）
      • getLogCallerFromException(): 例外オブジェクトから呼び出し元情報を抽出（例外ハンドラーで使用）
    • 実装上の流れ:
      • ExLogのプロセッサで extra['log_caller'] に設定（Monologの LogRecord はプロパティが固定で、プロセッサが追加できるのは context か extra のみ）
      • フォーマッタで extra から取り出してトップレベルの log_caller フィールドとして出力（"file:line" の文字列形式）
      • 元の extra['log_caller'] は削除され、最終出力では extra に含まれない

    • $callerOverride 引数を使用することで、自動検出された呼び出し元を明示的に上書き可能（通常は不要）

    • ペイロードの取得

    • ミドルウェア（LogRequestPayload）でリクエストのペイロード（request()->all()）を取得し、リクエスト属性に保存する
    • 別のミドルウェア（LogPerformance）でHTTPリクエストログ（http.request）のcontextにペイロードを直接展開する
    • ExLog::log()で一元的にサイズ制限とマスク処理を適用する（すべてのログ出力に共通）
    • 実装方法:
      • ミドルウェア（app/Http/Middleware/LogRequestPayload.php）でrequest()->all()を取得し、リクエスト属性に保存（例: $request->attributes->set('log_payload', $payload)）
      • ミドルウェア（app/Http/Middleware/LogPerformance.php）でHTTPリクエストログのcontextにペイロードを直接展開
      • ExLog::log()でcontext全体にサイズ制限とマスク処理を適用
      • HTTPリクエストコンテキスト外（CLI、キュー処理など）ではペイロードを取得しない

    • サイズ制限（config/logging.phpで設定可能、ExLog::log()内で実装）：

      • 個別の値の文字列長: 1,000文字（超過時は末尾を省略）
      • 配列の深さ: 5階層（超過時は深い階層を省略）
      • 全体のコンテキストサイズ: 10KB（超過時は主要キーのみ記録）
      • ファイルアップロード（UploadedFile）はファイル情報のみ記録（ファイル名、サイズ、MIME）
      • Eloquent Modelはクラス名とIDのみ記録（例: App\Models\User#123）
      • Collectionは要素数のみ記録（例: Collection(10 items)）
      • 例外オブジェクトはサイズ制限から除外（Monologが自動的に処理）
      • 処理順序: サイズ制限 → マスク処理の順で適用される

    • パフォーマンス情報の取得

    • ミドルウェアでリクエスト開始時刻を記録し、プロセッサ（PerformanceProcessor）で応答時間を計算してログレコードに追加する
    • 実装方法:
      • ミドルウェア（例: app/Http/Middleware/LogPerformance.php）でリクエスト開始時刻を記録（セッションやリクエスト属性に保存）
      • プロセッサ（例: app/Logging/Processors/PerformanceProcessor.php）で応答時間を計算し、ログレコードのextraに追加
      • プロセッサは各チャネルのtap設定で登録する

    • これにより、すべてのログ出力に自動的に応答時間が含まれ、サーバーログとUXログの両方でパフォーマンス情報を記録できる

    • HTTPステータスコードの取得

    • ミドルウェアでレスポンスオブジェクトのステータスコードをリクエスト属性に保存し、プロセッサ（WebRequestProcessor）で取得してログレコードに追加する
    • 実装方法:
      • ミドルウェア（例: app/Http/Middleware/LogPerformance.phpまたは専用ミドルウェア）でレスポンスオブジェクトのステータスコードをリクエスト属性に保存（例: $request->attributes->set('http_status', $response->getStatusCode())）
      • プロセッサ（例: app/Logging/Processors/WebRequestProcessor.php）でリクエスト属性からHTTPステータスコードを取得し、ログレコードのextra.http_statusに追加
      • プロセッサは各チャネルのtap設定で登録する
    • これにより、すべてのログ出力に自動的にHTTPステータスコードが含まれ、正常レスポンス（200など）も含めてすべてのログでHTTPステータスを記録できる

    ログの構造

    出力順序とフィールド一覧（ラインログ・JSONログ共通）

    項目 子項目 型 説明 例 自動付与
    datetime - string 日時（ISO 8601形式、ラインログでは [YYYY-MM-DD HH:mm:ss] 形式） "2025-11-19T11:40:02.344438+09:00" ○
    channel - string チャネル名 "site" ○
    log_level - string ログレベル "INFO" ○
    session_id - string セッションID（セッション開始済みの場合のみハッシュ化して表示。セッション未開始時は N/A を返す。ラインログでは [session_id] 形式） "359c9852" ○
    uid - string リクエストID（RequestUidProcessorで取得。UidProcessor の薄いラッパ。request_idとも呼ばれる。ラインログでは [uid] 形式） "297f174" ○
    user_id - integer/null ユーザーID（AuthenticatedUserProcessorで取得。Auth::user() 等から ID を取得。ログインユーザーが存在する場合のみ出力。JSONログでは未ログイン時はフィールド自体が省略、ラインログでは空の [] が表示） 1234 or [](ラインログ) △
    http_method - string HTTPメソッド "GET" ○
    http_status - string HTTPステータスコード（数値文字列、ログ出力時点でレスポンスが未確定の場合は "-"） "200" or "-" ○
    path - string リクエストパス（先頭 / 付き） "/test/logs/site" ○
    message - string ログメッセージ（英語ドット区切り形式を推奨） "http.request" -

    実装ステップ

    1. config/logging.php にチャネル定義を追加し、各チャネルの tap 設定でプロセッサとフォーマッタを登録する。
    2. プロセッサ（ExceptionProcessor、RequestUidProcessor、SessionIdProcessor、AuthenticatedUserProcessor、WebRequestProcessor）は各チャネルの tap 設定で登録する
    3. フォーマッタ（LineFormatter、JsonFormatter）も tap 設定で登録する
    4. これにより、チャネルごとに異なるプロセッサを適用でき、設定が config/logging.php に集約される
    5. 各ドメインのサービス層で Log::channel() から ExLog へのリファクタリングを実施し、命名規則とチャネル選択を統一する。

    ログ出力例

    • ExLog を利用して、メッセージとコンテキスト配列を渡す。
    use App\Logging\ExLog;

// 明示チャネル無しの呼び出し（すべて site チャネルに出力）
ExLog::info('order.created', [
    'order_id' => $order->id,
    'user_id' => $order->user_id,
]);

// 明示的にチャネルを指定（指定されたチャネルのみに出力）
ExLog::channel('payment')->warning('payment.retry_failed', [
    'order_id' => $order->id,
    'attempt' => $attempt,
    'provider' => $provider->name,
], ['provider']); // 第3引数でマスク対象のキーを指定

// マスク処理の例
ExLog::info('user.registered', [
    'email' => $user->email,
    'phone' => $user->phone,
], ['email', 'phone']); // 明示的にマスク対象を指定
    • コンテキストに配列や DTO の toLogContext() を渡すと、ラインログでは [key: value]、JSON ログではそのままキー・値として出力される。
    • マスク処理の動作:
    • ExLogで第3引数（$mask）を指定しない場合：マスク処理は行われず、すべての値がそのまま出力される
    • ExLogで第3引数（$mask）を指定した場合：指定されたキーのみマスク処理が適用される
    • Log ファサードの直接使用: ExLogの呼び出し元検出などの独自ロジックをバイパスしたい場合や、より低レベルなログ制御が必要な場合は、Log ファサードを直接使用できる。ただし、プロセッサやフォーマッタは同様に適用される。

    ログ出力一覧（自動処理）

    リスナー / ミドルウェア イベント ログレベル メッセージ 説明
    LogPerformance（ミドルウェア） HTTPリクエスト（通常） info http.request ルート解決結果（controller@method / invokable / closure）をもとに呼び出し元情報を付与して記録。Livewire内部リクエストは完全に除外。業務上重要なLivewire操作は各コンポーネント内でExLog::info()を手動呼び出し。
    ExceptionListener HTTP 例外（4xx） info http.client.error クライアント側の問題（不正なリクエストなど）。システムエラーではないためinfoで記録。
    ExceptionListener HTTP 例外（5xx） error http.server.error システムエラー。例外情報（file、line、trace）は自動的にexceptionオブジェクトとして付与される。
    TransactionListener トランザクション開始 debug transaction.begin 接続名とトランザクションレベルをcontextに含める。
    TransactionListener トランザクションコミット debug transaction.committed 接続名とトランザクションレベルをcontextに含める。
    TransactionListener トランザクションロールバック warning transaction.rollback 監視用のアラート閾値を設定しやすくするためwarningで記録。
    TransactionListener 未完了トランザクション error transaction.unfinished リクエスト終了時にトランザクションレベルが0より大きい場合に記録（キュー／バッチは未対応）。

    種別 代表的なケース 推奨ログレベル メッセージ例 備考
    ユーザー操作（CRUD） 画面上の登録・更新・削除などの完了時（例: 商品登録、会員情報更新、退会処理など） info admin.operation, member.operation, cart.operation 画面アクセス自体はhttp.requestで自動取得されるため、明示ログでは副作用のあるCRUD完了のみを対象とする。
    業務ステップマイルストーン カート→注文確認→決済選択→決済実行など、業務フローの主要ステップ完了 info order.step.confirmed, order.step.payment_selected 「ユーザーがどのステップまで進んだか」を追いたい単位のみ記録し、細かいUI操作は含めない。
    キャンセル・例外フロー 注文キャンセル、出荷取消、承認却下など通常フローから外れる操作 info order.canceled, shipment.reverted, approval.rejected 正常フローから外れ、業務影響の大きい操作は必ず記録する。
    メール送信系 通知メール・確認メールの送信開始／完了／失敗 info / critical mail.sent, mail.failed 業務上重要なメール（本登録、出荷通知など）は必ず記録する。失敗時はcriticalでアラート対象。
    外部API呼び出し 決済API・在庫APIなど外部サービスとの通信結果 info / error payment.request, payment.failed, inventory.api.error リクエストIDや外部側コードなど、調査に必要な最小限の情報を付与して記録する。
    ドメインイベント（Event） 注文確定、支払い失敗、サブスクリプション解約などのビジネスイベント発生時 info / error event.order.placed, event.payment.failed, event.subscription.canceled 「何が起きたか」を業務用語で表現する。頻度の高い技術的イベントは対象外とし、本当に重要な出来事のみ記録する。
    リスナー（Listener） イベントを受けて通知送信や別Workflow起動などの副作用を実行した結果 info / error listener.order_placed.notifications_sent, listener.payment_failed.workflow_started 副作用処理の成功/失敗を簡潔に記録し、二重実行や取りこぼしの調査に使う。
    通知（Notification） メール・Slackなどの通知送信 info / error notification.mail.sent, notification.mail.failed, notification.slack.sent 誰にどのチャネルで通知したか、失敗時の原因を追跡できる粒度で記録する。
    CSV入出力 管理画面からのCSVインポート・エクスポートの開始／完了／失敗 info / error csv.import.started, csv.import.failed, csv.export.completed 対象テーブルや件数、ファイル名などを含めて記録し、不整合や取り込みミスの調査に使う。
    バッチ操作 定期ジョブ／手動実行ジョブ（在庫同期、再計算など）の開始／完了／失敗 info / error batch.daily_job.started, batch.daily_job.failed, batch.inventory_sync.completed 大量データに影響する処理の実行履歴と結果を記録し、後から「いつ／どのジョブが／どう失敗したか」を追えるようにする。
    予兆・フォールバック リトライ成功、代替処理に切り替えた場合など notice / warning payment.fallback.used 将来の障害兆候になりうるが、即時対応までは不要なもの。
    エラー系（要対応） 処理失敗、外部APIエラー、想定外例外など error / critical cart.error, payment.failed アラート対象になりうる事象。業務影響に応じてレベルを使い分ける。

    Workflow / イベント周りのログ責務

    Workflow やドメインイベント周辺で ExLog を使う際の責務分担は次の通りとする（Eloquentオブザーバーは別設計とする）。

    層・仕組み 主な役割 ログの粒度・目的 代表メッセージ例
    Workflowクラス 複数ステップを跨ぐビジネスプロセスの進行管理 ワークフロー全体の開始・ステップ完了・失敗など「マイルストーン」を info / error で記録 workflow.order_placement.started, workflow.order_placement.step.payment_processed, workflow.order_placement.failed
    ジョブ（Workflowのステップ） 各ステップの非同期実行 ステップごとの開始・完了・失敗、リトライ情報を必要に応じて記録 job.reserve_inventory.started, job.reserve_inventory.completed, job.reserve_inventory.failed
    ドメインイベント（Event） ビジネスイベントの発火（注文確定、支払い失敗など） 「ビジネス上の出来事」として重要なイベントのみを info / error で記録 event.order.placed, event.payment.failed, event.subscription.canceled
    リスナー（Listener） イベントに応じた副作用処理（別Workflow起動・通知など） 副作用の結果（成功 / 失敗）を簡潔に記録 listener.order_placed.notifications_sent, listener.payment_failed.workflow_started
    通知（Notification） メール・Slackなどの送信 通知送信の開始・成功・失敗を info / error で記録 notification.mail.sent, notification.mail.failed, notification.slack.sent

    方針として、Workflow/ジョブは「処理フローのどこまで進んだか」を、イベント/リスナー/通知は「ビジネス上何が起きたか」「誰にどう通知したか」を表現するログを担当し、内部の細かい技術ログは必要に応じてサービスクラス側で記録する。
